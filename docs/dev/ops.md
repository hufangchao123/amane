# 媒体运维功能 (字幕 / 洗版 / 通知)

> 阶段包: `src/amane/subtitles`、`src/amane/library/wash`。
> 本文只写跨模块契约与仍生效的禁止事项; 端点形状、字段与默认值读源码或 `web/openapi.json`。
> 路由见 [api.md](api.md), 任务边界见 [task-system.md](task-system.md), 库文件与回收站见 [data-model.md](data-model.md)。

## 边界

| 包 | 职责 | 不变量 |
|----|------|--------|
| `subtitles` | 从字幕来源取回字幕文件 | 放置一律经 `organize.subtitles`; 不直接改库内路径 |
| `library/wash` | 同组多份文件择一保留, 其余入回收站 | 移动必须持 `LibraryTaskLocks`; 落选只搬进 `.amane_wash`, 不 `os.remove`; 真删只发生在到期的清理 |

`library/wash` **不**并入 `amane.library` 的公共导出面: 配置层 (`config/manager.py`) 依赖 `library`, 汇入会形成循环导入。路由与 handler 直接用完整包路径导入。

## 任务类型

`subtitle_fetch` / `wash_scan` / `wash_apply` 三类经 `AsyncWorker` 消费, 由 `app/runtime.py::build_handlers` 注册。
`wash_scan` 与 `wash_apply` 是**两个** handler (`WashScanHandler` / `WashApplyHandler`) 与两套 payload: 扫描只读出候选, 执行按候选移动; 前者不取 `LibraryTaskLocks`, 后者必须取。

`WashApplyPayload` 的三组入口可以同时给: `restore_ids` 与 `purge_ids` 来自回收站列表, `group_keys` 来自候选列表, 执行顺序固定为还原 → 清理 → 洗版; 三者全空表示按当前策略重算后执行全部候选, 只带还原或清理时不顺手洗全库。

- 长循环、批量搬移、批量下载、批量移动一律在这些 handler 里, 不进请求线程。
- 同步 I/O (网盘列表、字幕下载、文件移动、打包) 走 `utils/threads.py` 的 `@in_thread`, 遵守 5 ms 事件循环预算。
- 后继任务只经 `TaskResult.followups` 进入完成事务, 不直接写队列; 任务判失败或崩溃时仍要排的后继走 `TaskHandler.failure_followups`, 由 worker 单独入队 (它们不属于失败任务的子任务)。
- `wash_apply` 与 `delete` / `organize` 争用同一库路径, 必须共享 `LibraryTaskLocks`。

## 数据与备份

**不做数据备份**: 全部状态都在 `data_dir` (容器里的 `/data`), 由部署方用宿主快照或自己拷该目录负责; 应用只保留迁移前的 `amane.db.pre-migrate-*.bak` (`db/sqlite_migrate.py`)。运行中直接 `cp amane.db` 不安全 (WAL 未合并), 手工备份须用 online backup 接口。

## 洗版的分组与回收站

分组键含库 id、番号、CD 与有无码, 本地文件与 STRM 各成一组, 跨库不合并。

择一按 `wash.prefer` 给出的**维度顺序**逐项比较, 排在前面的维度先分出高下: `quality` 内部仍是「清晰度档位 → 码率 (`size/duration`, 时长缺失时跳过该项而不拿体积冒充) → 体积」, `subtitle` 比较「文件名带中文字幕标记 → 有外挂字幕 → 没有」, `largest` / `newest` / `oldest` 各比一个单值。只填一个维度等于旧的单选行为, 旧配置里的字符串照旧接受。容器与路径永远是最后两档, 只为让同样的输入每次都选出同一份。

字幕维度按路径与索引里的两列判定: 文件名里的 `-C` / 中字 / 简中这类标记算「带中文字幕」, `MediaFile.has_external_subtitle` 算「有外挂」; `-cd2` / `-ch` 之类不会被误当成 `-C`。STRM 的 `size` 恒为 0, 只比同目录、容器与路径, 绝不进体积比较; 显式把 `subtitle` 放进顺序时它才按字幕比 —— 云盘那份有没有中文字幕是实情, 档位与体积不是。`wash.min_size_mb` 同样只筛本地文件: 指针只有几百字节, 按体积过滤会把整类排除, 于是 STRM 组只在有两份以上指针时才成形。

回收站落在库根的**父目录**: `<库根父目录>/.amane_wash/<库根名>/<local|strm>/<库内相对路径>`, 与库同盘因此多为改名; 目标已存在时计入 `skipped`, 不覆盖。扫描、清点与空目录判定把 `.amane_wash` 与 `.amane_trash` 一并忽略 (`library/rules.py::is_in_trash`)。还原靠 `group_key` 里的库 id 与上述布局反推原位: 库被删除或重建后 id 变化, 还原会失败, 文件留在回收站可手工取回。

洗掉的文件**连同索引行一起消失**: 洗版搬走时删掉那条 `MediaFile`, 否则播放与清理仍按旧路径解读。还原是反向的: 文件搬回原位后重建索引行, 能解析出番号就顺手挂回已有元数据 (标 `scraped`), 于是不需要再刷新一遍才出现在面板里。

到期清理按记录逐条判定: 删掉或文件已缺失的记录推进 `purged`, 删失败 (权限、占用) 的文件仍在回收站, 记录保持 `trashed` 等下一轮重试 —— 推进 `purged` 会同时抹掉还原入口与重试机会。清理与还原取同一把库锁, 同一条记录不会被「真删」与「还原」同时处理。

## 洗版的自动化

三个开关都在 `wash` 段, 默认全关:

- `auto_on_ingest`: 整理或刮削后转移把文件送进库根之后, 各排一次只读的 `wash_scan`。分组要等同番号的第二份进来才成形, 定时扫描的间隔里重复会白占一份空间; 扫描本身不改盘上内容, 因此不取库锁。
- `auto_execute`: 扫描把**没有争议**的本地组直接排 `wash_apply`。判据只有两条, 且都要求保留者严格更好: 分辨率档位更高 (4K 对 1080p), 或同档位、两边时长都可读且保留者比每一份落选者大出 `auto_execute_min_gain_percent` 个百分点。档位相同而体积接近时差异可能来自压制风格、音轨或字幕补丁, 那不是自动该决定的事, 留在清单里由人挑。STRM 组恒不自动: 指针没有画质, 留哪份牵扯播放器兼容与云端来源。
- 时长读不出来的组一律不自动执行: 拿不出时长就无法证明码率更高, 体积不能替代它。

自动执行不等于删除: 动作只是把文件移进 `.amane_wash`, 真删仍由 `keep_days` 到期清理执行, 判错也可还原。扫描结果的 `auto_groups` 记录这次自动交出去了几组, 其余候选照旧出现在洗版页。

## 人对某一组的决定

`wash_choices` 存两件事: 钉住哪一份 (`keep`, 带 `keep_path`), 或者「两份都留着」(`ignore`)。扫描与执行每轮都先读这张表再分组:

- `ignore`: 该组的落选者被清空, 于是 `drop_paths` 为空、`bytes_freed` 为 0, 自动执行也不会选中它; 组仍出现在候选列表里, 可以撤销。
- `keep`: 钉住的那份成为保留者, 其余照常进回收站。钉住的那份已经不在了 (被删或被洗掉) 时按算法结果处理, 不因为一条过期决定卡住整组。

分组键随文件增删变化, 因此决定可能变成孤儿: 扫描结束时把对不上任何组的键清掉。执行路径读的是「不含 `ignore` 组」的视图, 列表页读全部 —— 少了这一层, 一次「全部执行」就会把使用者明确要留的那两份搬走。

## 数据

`wash_records` 一行对应一次「留一个、移一个」, 指向回收站内的实际位置; 只由洗版任务写入, 路由只读。

`wash_choices` 存人对某一组的决定 (`keep` / `ignore`), 由 `PUT /api/wash/choices` 写入、`DELETE /api/wash/choices/{group_key}` 撤销。

面板时代的状态文件 (`115-transfer-state.json` 等) **不再读写**。

## 字幕缺口的两种口径

`GET /api/subtitles/status` 把缺外挂字幕的成片分成两份:

| 字段 | 含义 | 用途 |
|---|---|---|
| `missing` | 单片 (文件名与父目录都没有分卷标记) 且没有任何字幕 | 补全任务的目标集合, 巡检的缺口数 |
| `multi_disc` | 带显式分卷标记 (`-CD2` / `PART1` / 父目录 `CD1`) 且没有任何字幕 | 只报数, 不抓 |

分卷不抓的理由: 字幕站给的是整片的字幕, 与拆开的文件时间轴对不齐, 抓下来也放不对位置。
判定只看显式标记 (`subtitles/targets.py::is_multi_disc`), 不按「番号带尾号」推断 —— `AD-1.mp4`
的尾号属于番号本身。补全任务遇到分卷时直接记为跳过, 不发请求。

## 番号里的下载源前缀

有的下载源会在真实番号前面塞一段随机字母 (`YRNKNKJDVAJ-683.mkv`), 解析出来就成了假番号,
刮削与字幕搜索都跟着失准。`parsing/file_info.py::_JUNK_PREFIXES` 逐个列出这类前缀, 命中即剥掉。

只认列举的值, 不做「剥到看起来像厂牌为止」的猜测: 厂牌名长度与形态差异太大 (`300MIUM` 含数字、
`MBRBN` 五个字母), 猜测式剥离会把合法番号改坏。遇到新的前缀加一行即可。

## 转写生成字幕

外部站都没收录时, 可以把音轨交给外部的 Whisper 服务转成原文, 再逐句译成中文. 转写引擎**不装进镜像**:
机型与算力差异太大, 同一份音轨在 CPU 上要跑几十分钟. 镜像里只多一个 `ffmpeg` 用来抽轨.

判据与边界:

- 端点按 OpenAI 兼容契约要求 `/audio/transcriptions` 且 `response_format=verbose_json`: 没有分段就拼不出时间轴,
  只有整段文字的应答直接算失败 (``WhisperError``: 没有返回分段).
- 抽轨固定 16 kHz 单声道 PCM, 与 Whisper 的训练输入一致, 上传体积也最小.
- 只要 ``subtitles.generation.enabled`` 且端点非空才跑; 要求翻译时 ``llm.enabled`` 与 ``llm.api_key`` 必须都在,
  否则整轮直接失败并说明原因 —— 让每一份文件各失败一次只会刷一屏同样的日志.
- 目标口径与补全一致: 只挑 ``has_subtitle=false`` 的已刮削文件, 分卷跳过, 已有外挂字幕跳过, 超过
  ``max_file_minutes`` 跳过.
- 落位写在**视频自己旁边** (``<视频 stem>.<zh|音轨语言>.srt``), 不走库模板: 转写产物与视频一一对应,
  按模板重新命名只会让它离开自己那一份. 写盘在库锁内完成, 复查路径失败就跳过, 不覆盖已有字幕.
- 生成的字幕首行写 ``机翻 (Whisper)``: ``subtitles/models.py`` 的 ``_MACHINE_MARKS`` 认这个标记,
  界面与来源排序据此不把它当人工翻译.
- 翻译分批 (每批 40 行), 只换正文不动时间轴; 行数对不上时保留原文并记 warning —— 错位字幕比没翻译更糟.

## 字幕的来源

按 `subtitles.providers` 的顺序逐家尝试, 取到第一份就停; 一家失败换下一家, 只有临时失败 (超时、断连、429/5xx) 才在同一个来源上重试。

| 来源 | 鉴权 | 取法 |
|---|---|---|
| `subtitlecat` | 免鉴权 | HTML 三跳: 搜索页 → 详情页 → 直链 `.srt` |
| `avsubtitles` | 免鉴权 | HTML 四跳: 搜索页 → 影片页 → 字幕详情页 → 确认页, 再下压缩包 |

`avsubtitles` 的下载接口只认会话 cookie, `subid` 与 `revid` 缺一不可: 详情页给出 `revid`, `download_page.php`
让会话里有记录, 少了这一步 `download_sub.php` 只会 302 到 `error_403.php`。会话由 `WebClient` 的 cookie 罐维持,
因此确认页必须真的走一遍。站点只有 `zh` / `ja` / `ko` 三个语言段, 配置里的 `zh-CN` / `zh-TW` 都映射到 `zh`;
该片没有中文条目时不下载日文或韩文 —— 本包补的是中文字幕。

## 字幕补全的目标

只挑 `status=scraped` 且没有外挂字幕的媒体文件; 落位要按番号找到元数据条目, 缺条目记为失败而不是缺口。同一目录已有一份字幕后, 后续文件按「已有外挂字幕」跳过, 因此一次任务通常只落一份。

落位后立刻按库的 `subtitle_extensions` 复查一次: 落下的扩展名不在清单里就记失败并说明原因 —— 文件在磁盘上但库不认, 不报错就会每轮重抓同一份。补到字幕后排一次 `MEDIA_REFRESH`, 否则媒体服务器不会重读目录。刮削成功且字幕补全启用时, 也给这个缺字幕的文件排一次 `SUBTITLE_FETCH`; 字幕巡检算出缺口 (`missing > 0`) 且扫描范围是单库时同理, 多库巡检不排 —— 不知道哪一库缺得多, 逐库排会把额度一次花光。

还在输入目录里的文件 (刮削后尚未转移/整理) 也允许补字幕, 但落位不能按库模板算: 默认模板用绝对路径
`{link_dir}/{raw_srt_name}.{ext}`, 基准目录只有库根, 算出来的路径在库外会抛「路径越界」。这类文件把字幕
落在它自己旁边 (`<视频 stem>.<语言>.<ext>`), 随后被转移与整理一并带走。取库锁之后会重读一次媒体行, 因为
转移与整理会改路径, 用任务开始时的旧路径会往已不存在的位置写。

外部站点地址 (115 webapi、字幕来源) 的连接都经 `net/egress.py` 判定: 默认拒绝内网地址, 这是防 SSRF 的硬约束, 本地联调要连伪造站点时只能在测试侧放行回环地址。

## 配置

`subtitles` / `wash` / `notify` 三个 section 挂在 `HotSettings`, 由 `/api/config` 的 schema 直接出表单。

- 密钥只放 section 内的字符串字段, 不进日志、不进任务 payload。
- `enabled` 与实际可用分离: 缺凭据或目录时服务层报未启用, 任务不会半途失败。
- 关闭某项功能不等于留下残留任务: 派生入口先看 `enabled`。

## 端点与提交

三个功能各有 `GET /api/{subtitles|wash|notify}/status` 只读端点, 任务入队统一走 `POST /api/tasks` 的判别联合。

三个提交模型 (`SubtitleFetchSubmission` / `WashScanSubmission` / `WashApplySubmission`) 存在, 是为了满足 `tests/api/test_tasks.py` 的两条不变量: 每个 `TaskType` 都必须有提交模型 (`TaskSubmission`) 与结果模型 (`TaskResultPayload`)。前端把它们列为 `PanelOnlyTaskType`, 不出现在通用提交弹窗里 — 由各自页面按钮直接调 SDK。

`handlers/models.py` 里的 Payload / Result 与 `handlers/*.py` 里的 handler 分离, 结果模型带 `type: Literal[TaskType.X]` 判别字段。新增任务类型要同步五处, 少一处就有编译期或测试期报错挡着: `TaskSubmission` 联合、`TaskResultPayload` 联合、`api/support/task_resolve.py::resolve_submission` 的 `match`、`web/src/lib/exhaustive-maps.ts` 的 `TASK_TYPES`、`web/src/lib/task/display.ts` 的 `TASK_ICONS`; 另有 i18n 的 `settings.json`(配置字段) 与 `tasks.json`(提交字段 + `filters.*`) 两处编译期穷举检查。

### 洗版择一的策略

同番号下的前編/後編、合集/全集、特典/花絮按文件名关键词各自成组 (`library/wash/model.py::_PART_TOKENS`):
与正片互洗会把一整段内容洗掉。关键词是常量表, 认不出就仍按同番号归并 —— 宁可漏洗, 不可错洗。


`wash.prefer` 是一个**有序的维度列表**, 排在前面的先分出高下, 只填一项等于旧的单选行为:

- `quality`: 拆成两截 —— **分辨率档位**排在最前, **码率与体积**退到所有维度之后;
- `subtitle`: 文件名带中文字幕标记 (`-C`、中字、简中一类) → 同目录有外挂字幕 → 都没有;
- `largest` / `newest` / `oldest`: 只看体积或修改时间 (拿不到时间排在最后)。

`quality` 之所以拆开: 档位不同是观感上的硬差距, 先分出来; 同档位时码率与体积的差别往往只是压制风格与音轨, 让位给使用者排在其后的维度。于是「先画质后字幕」的实际顺序是 档位 → 字幕 → 码率 → 体积: 1080p 带中字的 800 MB 会胜过 1080p 无字幕的 1.6 GB, 但不会为了字幕把 4K 换成 720p。反过来把字幕排在画质之前就是字幕压倒一切 (包括档位)。

每个维度只在前面都打平时才起作用。列表末尾固定是容器与路径, 只用来保证同样的输入每次选出同一份 —— 只选单维度时, 该维度相同时才轮到它们。

字幕维度的取值来自三处: 文件名的中文标记、`media_files.has_external_subtitle`、`media_files.has_subtitle_in_name`。「中文字幕」比「有字幕」靠前, 因为库里缺的通常是中文, 一份英文字幕顶不上。自动执行的准入也随之收紧: 落选者带着更好的字幕时不算没有争议, 哪怕保留者的分辨率更高。

`wash.strm_prefer` 单独管 STRM 组: `path` (默认) 只比容器与路径, `definition` 改成按文件名里的档位 (等于接受「信文件名」这个前提, 默认不用), `newest` / `oldest` 比 `.strm` 的修改时间。体积与码率永不参与 STRM 比较 —— 指针的体积是几百字节, 比大小会把云端的高码率那份洗成低码率的。

### 字幕巡检的判据

`SUBTITLE_AUDIT` 遍历库内已入库的文件, 逐目录比对视频与字幕, 输出两项互不校正的计数: `missing` 只算
已刮削 (`SCRAPED`) 且 `has_subtitle` 为空的行 —— 未刮削与失败的行不进补全队列; `orphans` 取自磁盘 —— 字幕文件名不以任何视频的 stem 开头即算配不上, 因为落位规则是
`<视频 stem>.<语言>.srt`. 判据只看文件名, 不判「来源番号与目标番号是否一致」: 那要下载历史, 库内没有这份历史.

扫描的目录只取已入库文件所在的目录, 扩展名取 `libraries.subtitle_extensions` (空列表跳过). 巡检只出清单,
不移动文件, 因此不取库锁; 清理配不上的字幕在回收站运维里做.

## 115 网盘的中转不在本应用内

115 网盘的网盘侧搬移 (把离线落点搬进 STRM 成品目录) 由下游的 STRM 工具承担, 本应用不读网盘、不存网盘凭据、也不发起网盘请求: 离线下载完成不产生下游能用的创建事件, 只有搬移产生的移动事件才会让它生成 `.strm`。

## 定时入口

`scheduler/cron.py::_execute_task` 的 `match` 有三个媒体运维分支, 每一支只做「把例行转成任务」:

| 例行类型 | 入队任务 | 载荷 |
|---|---|---|
| `wash_scan` | `TaskType.WASH_SCAN` | `WashScanPayload(kind=…, library_id=…)` |
| `wash_purge` | `TaskType.WASH_APPLY` | `WashApplyPayload(purge_ids=到期记录 id)` |

`wash_scan` 只入队只读扫描: 洗版是破坏性动作, 定时任务只产出候选, 由人决定何时执行 `wash_apply`。

`media_refresh` 的例行有独立分支 (`RoutineType.MEDIA_REFRESH` → `TaskType.MEDIA_REFRESH`), 只让媒体服务器重扫, 不触碰库文件, 因此不列在上表。

## 历史回收站

`.amane_trash` 是早期版本的删除落点: 现在的删除直接删文件, 不再往里搬 (见 `data-model.md`), 新部署不会产生这个目录。目录里只有相对路径, 没有原位信息, 因此应用**不提供还原, 也不提供清理**: 猜原位会把文件搬进别人的番号目录, 而按保留期批量删是用户盘上的不可逆操作, 交给使用者自己判断更安全。

扫描、监控、洗版与整理对 `.amane_trash` 的忽略照旧 (`library/rules.py::is_in_trash`), 所以遗留内容不会被当成新文件入库; 手动移出后按新文件重新入库。

## 演员头像校验

头像地址来自刮削, 站点换路径后库里会留下大量失效链接. `AVATAR_CHECK` 只查每个演员的**首图**: 首图可用说明来源还活着, 后面的备用地址不单独校验. 图片判定只看文件头, 覆盖 jpeg / png / gif / webp / bmp / svg 以及 avif 与 heic 的 `ftyp` 盒子 —— 站点近年常见 avif, 少认一种就会把有效链接判成坏图.

判定分三种, 只有 `broken` 允许清链接 —— 清空是不可逆动作, 而站点抖动与链接失效在客户端看起来一样:

| 结论 | 判据 | 可否清链接 |
|---|---|---|
| `ok` | 拿到字节且文件头认得出是图片 | — |
| `broken` | 内容不是图片; 下载失败且状态码是 404 / 410 | 可以 |
| `unknown` | 地址指向内网、协议不支持、超时、连不上、域名解析失败、其余 4xx 与 5xx | 不可以 |

内网单独成一种, 是因为本地媒体服务器常驻内网, 那不是坏链接, 清掉反而丢图. 状态码要在下载失败后再问一次 HEAD: 下载接口只回「失败」, 不给原因.

判定只读: 下载内容写进 `data/avatar-check/<随机段>/` 后立即删除, 整轮结束连空目录一起收. 目录带随机段, 是因为 worker 并发跑多个任务, 共用固定路径会互相读到写了一半的文件. 单张上限 8 MiB.

`clear_broken` 打开时把坏地址从 `image_urls` 里摘掉 (其余地址保留), 走 `remove_actor_image_url` 而不是 `update_actor`: 后者会把该字段并入手动字段锁, 一次「修坏图」就让后续刮削不再维护头像; 前者只改这一行, 不碰锁与来源, 也不会用旧快照覆盖并发写入的其它地址. 单个演员的意外异常计 `failed` 而不报废整轮, `failed > 0` 时任务判失败.

## 媒体库的自动刷新

`media_server.auto_refresh` 打开时, 六条会改盘上内容的路径共用一处判定 (`handlers/_common.py::media_refresh_followups`): 整理落盘、刮削后转移、洗版 (洗掉/还原/真删)、NFO 修补、删除、字幕补全. 未配置 `media_server` 或开关关闭时一条都不排 —— 那是「不想让 amane 动媒体服务器」, 与具体哪个任务无关. 洗版与 NFO 修补只在请求指定了单个库时刷新: 跨库任务没有可指向的库.

## 刷新的锁

`REFRESH` 与整理 / 删除 / 洗版 / 字幕落位共用 `LibraryTaskLocks`: 洗版搬到一半时刷新会把尚未搬走的文件判成「已消失」并删掉索引行. 因此整段扫描与索引维护都在库锁内, 同一库的刷新会排队等前者做完.

## 任务失败的通知

`notify.enabled` 打开时, 任务判失败或崩溃会额外排一条 `NOTIFY` 消息 (`kind=message`, 标题带任务类型, 正文取错误首段). 「通知」自身失败不再推, 否则地址配错就会自激; 入队失败只记日志, 不影响任务本身的失败处理.

## 写操作留痕

`AuditMiddleware` 在响应返回前把写方法 (POST / PUT / PATCH / DELETE) 的方法、路径、脱敏后的查询串、状态码、耗时与来源地址写进 `audit_records`; 写入失败只记日志, 不改写响应状态。留痕因此让每个写请求多一次插入, 换来的是没有排队丢失与没有后台任务的生命周期问题。留痕在鉴权中间件之外, 因此被拒的写请求也会被看到. 不过 401 / 403 只记日志、不落库: 那些请求没有发生写入, 逐条同步 commit 会被高频匿名请求放大. 端点抛未处理异常时响应是 500, 中间件在 `finally` 里照样留一行 —— 最该追溯的失败不能恰好缺席。

查询串按与日志同一套规则脱敏 (`utils/urls.py::redact_query`), 请求体与响应体不记录 —— 其中可能有密钥与个人数据, 体积也不可控。就绪检查、接入引导与长连接不记。

保留条数是常量 `AUDIT_KEEP`, 每累计写入这么多条就按时间倒序修剪一次 (单条 `DELETE` 带子查询, 不把待删 id 读进 Python), 因此表的上限是它的两倍; 写入端也不回读主键 —— 每个写请求只多一次插入与一次 commit. 修剪失败不清零计数, 下一条留痕会再试。`GET /api/audit` 只读分页, `DELETE /api/audit` 清空: 清空动作本身也会留下一条记录, 被清掉多少另记在日志里 (记录已删, 数量只能在日志里看)。留痕是事后核对手段, 不承担合规审计职责: 它不防篡改, 也不落远端。

## 通知

渠道表单、测试发送与最近推送都在设置页的「通知」分段里 (该分段由 `notify` schema 自动生成表单, 面板挂在表单下方), 没有独立页面。

`NOTIFY` 把一段标题与正文推到 `notify` 配置里的渠道, 四种渠道只在请求形状上不同 (`notify/channels.py` 一张表); `kind=digest` 时正文留空则由任务现算摘要: 队列计数、按类型的条数分布、媒体库与字幕缺口、洗版回收站可用量与占用、最近五条失败任务。摘要只查库, 不扫盘, 因此可以挂在例行上 (`NOTIFY_DIGEST`)。

地址由使用者在配置里填写, 常常指向内网 (自建 Bark / Server 酱代理), 因此这里**不放内网出站限制** —— 与抓站点的出站策略不同, 也不该相同。地址里可能带密钥, 所以 `notify.url` 进脱敏名单, 导出任务记录时会被替换。

每次推送写一行 `notify_records` (种类、渠道快照、标题、正文摘要、结果), 保留条数由 `notify.max_records` 决定, 超出部分在下一次推送时删除。推送失败只把任务标为失败并带上渠道返回码, 不回滚任何业务动作; 未启用或地址为空时不发请求, 直接失败并写明原因。

推送标题上限 200 字、正文上限 2000 字 (`handlers/models.py` 的 `NOTIFY_TITLE_LIMIT` / `NOTIFY_BODY_LIMIT`): 载荷整体进任务表的 JSON 列, 批量提交时若不设限会被写成几 MB。记录层另有 `BODY_LIMIT` 截断, 两者不同 —— 前者拒收, 后者只是留痕时缩短。渠道地址 (`notify.url`) 在配置阶段校验: 非空必须是 http(s)、有主机名、端口在 1-65535 且不超过 2000 字, 免得推送时才报错。发送阶段的任何异常 (端口越界、解析失败、TLS 失败, 乃至 anyio 包起来的 `ExceptionGroup`) 都折成失败结果, 只记日志不外抛 —— 通知失败不该炸穿任务, 也不该被当成可重试的业务错误。
摘要 (`kind=digest`) 按 `notify.sections` 逐段拼: `queue` 报最近 7 天的完成与失败、当前排队与执行中, 并附最近五条失败任务; `types` 报按任务类型的条数分布 (原有刮削整理与移植来的运维任务同列, 按条数取前 6 类); `library` 报媒体库文件数与缺外挂字幕数; `wash` 报洗版回收站条数与占用。勾空的段不查库, 全不选时只发标题。时间窗靠 `count_tasks(since=…)` 与 `count_tasks_by_type(since=…)`, 不扫盘也不读日志。


## NFO 修补

`NFO_PATCH` 改写已有的 NFO 文件, 分两类: `kind=thumbs` 给 `<actor>` 块补 `<thumb>`, `kind=directors` 删掉 `<director>` 行。两类都只碰磁盘文本, 不写数据库, 也不改库内索引; 手工搬动过目录的库同样适用。

缩略图取 `Actor.image_urls` 的第一条, 与媒体服务器上的演员图表同源; 演员在库内没有头像时计 `missing_image`, 不写半截标签。演员块已有 `<thumb>` 的跳过, 因此重复执行不产生变更。写入走同目录临时文件加 `Path.replace`, 中途失败不会留下半截 NFO。

`dry_run` 默认开启: 只扫盘并报出将改动的文件数与前十个文件名。真跑时按媒体库取 `LibraryTaskLocks`, 与整理 / 删除 / 洗版互斥。库目录不存在或 NFO 读写失败计 `failed`, 该文件跳过, 整轮继续。

`GET /nfo/status` 只报库内演员总数与其中带头像的数量, 以及可选媒体库; 待补条数必须先预演, 因为那要遍历磁盘, 不适合放在请求里。

计数与落盘一致: 只有写成功才累加 `changed` / `filled` / `removed`, 写失败只计 `failed`, 否则结果会报出没写进去的改动。临时文件带随机段并在失败时删除, 并发任务互不覆盖、也不留 `*.patch-tmp` 残骸。

## 下载中的文件

监控只看得到「文件出现了」, 看不到「写完了没有」, 因此两道闸门都在 `library/rules.py`:

| 闸门 | 挡住的形态 | 代价 |
|---|---|---|
| `PARTIAL_SUFFIXES` (`.!qB` / `.part` / `.crdownload` / `.download` / `.aria2`) | 下载器写在同名相邻文件里的半成品 | 无: 这些后缀本来就不是媒体扩展名, 顺带把清理清单的否决项也统一了 |
| `WatcherConfig.settle_seconds` (默认 5 秒, 0 关闭) | 文件已经叫 `.mkv` 但仍在增长 (qBittorrent 开启预分配磁盘空间时如此) | 完整文件晚 5 秒入库 |

体积判据在 `scheduler/watcher.py::_Handler`: 事件到达时记下体积与时刻, 防抖窗口过后每次检查都
重新 `stat`, 体积与上次不同就重置计时, 连续 `settle_seconds` 秒不变才放行。判据只覆盖监控
(事件驱动) 路径; 手动刷新是明确的一次性动作, 不额外等待。

清理清单把 `PARTIAL_SUFFIXES` 当否决项 (`library/cleanup/orphan.py::_VETO_EXTENSIONS`), 含这些
文件的目录不会进清理清单 —— 冷却期只保护正在写入的那一个, 暂停中的下载进度删掉不可恢复。

## 索引行何时算「文件没了」

刷新、整理、清理三处都按路径判「文件是否消失 → 删索引行」。判定一律走
`utils/path.py::disk_probe`（线程里用 `disk_probe.sync`）:

| `stat` 结果 | 判据 | 处理 |
|---|---|---|
| 成功 | 文件在 | 保留 |
| `ENOENT` / `ENOTDIR` | 确认不在 | 删行 |
| `EACCES` / `EIO` / `ESTALE` / 其它 | 不知道 | 保留, 计入结果里的 `unreadable`, 下一趟再判 |

`Path.exists()` 把这三类都吞成 `False`, 挂载抖动一次就能清掉整库索引, 因此不能再用它做这个判定。
清理还多两道:

- 库根自身读不到 (掉盘 / 挂载没起来) 时整库跳过, 不按「路径不存在」删行;
- 删行在库锁内重新读一次记录, 删什么按最新状态算, 不用锁外的快照; 分批处理时不按批大小推进
  `offset` (删掉的行会让后面的记录被跳过)。

## 整理与清理不越界

- 整理只处理「监控范围内登记的行」: 库里位置合法但不在扫描范围的行 (例如历史遗留的库外路径)
  不计入 `organized`, 只记一条 warning;
- 显式填了成功目录 (`scrape_ok_dir`) 时, 刮削后转移不排 `ORGANIZE`: 那是使用者自己排好的目录树,
  再按模板整理一遍会把它打散. 成功目录留空、落点等于库根时才排整理;
- 删除与剪枝都拒绝回收站目录: 上游的 `.amane_trash` 只拒绝目录本身 (清空它是使用者的动作),
  洗版的 `.amane_wash` 在可还原窗口内一律拒绝 —— 删掉会让 `wash_records` 指向不存在的文件;
- 整目录删除按内容展开时跳过回收站目录与 `PARTIAL_SUFFIXES` 残件, 与清单扫描同一口径。

## 刮削后转移


库配置 `scrape_transfer` 打开后, 每次刮削结束都排一个 `SCRAPE_TRANSFER`: 成功时作为 `followups` 随完成事务入队, 失败 (含 handler 崩溃) 时由 worker 经 `failure_followups` 入队。两处都 `priority=-1`, 不抢占交互提交的任务。

三个目录都可空, 落点由 `library/transfer.py::scrape_transfer_destination` 判定:

| 配置 | 语义 |
|---|---|
| 只填成功与失败目录 | 库根 (`path`) 就是待整理目录: 刮削通过搬去成功目录, 失败搬去失败目录 |
| 再填输入目录 | 文件从输入目录进来, 库根成为成品目录: 通过后搬进库根, 失败搬去失败目录 |
| 成功目录留空 | 通过后留在原地 (有输入目录时即搬进库根); 文件本来就在目的目录时不搬, 只记一句说明 |
| 失败目录留空 | 失败后留在原处, 便于直接重试 |

三者不能全空, 至少填一个 (422)。输入目录必须在库根之外且与成功/失败目录互不重叠 (相等或互相包含都拒绝): 重叠时搬运结果会被扫描重新登记, 或刚搬出的文件被扫回, 形成来回搬运。成功与失败目录可以等于库根 (等于就是留在原地), 但不能落在库根之下, 那样搬过去的文件会被重新登记成新文件; 两者也不能相同。

库上的 `keep_source_dirs` 默认关闭: 文件搬走后空的来源目录会被逐层删掉, 只保留库根, 与上游整理行为一致。打开后整理 (`ORGANIZE` 的 `prune_empty_dirs` 仍要开着且有实际腾空) 与刮削后转移都不删空目录, 用于下载器复用固定目录或来源目录是挂载点的场景。

扫描与监控覆盖库根, 填了输入目录时**同时**覆盖输入目录: 整库刷新会按库根跑一趟后再补一趟输入目录 (子目录范围的刷新不动输入目录), 监控的观察点放在输入目录。库根内搬空的目录会删掉, 库根本身保留。

搬走的是视频与它同前缀的附属文件: 前缀取视频 stem 与解析出的番号两者, 因此整理前的 `ABC-123.nfo` 与整理后的 `ABC-123-1080p.srt` 都能跟上; 后缀须在库的字幕扩展名或附属集合 (`.nfo` / 图片) 内, 同前缀的另一份视频靠后缀排除。目的目录重名加序号, 不覆盖已有文件。

库内记录改指新路径, 文件仍在库里被跟踪: 可再次刮削、可再整理、可洗版。输入目录里搬空的那一层删掉, 库根保留。整批或单个文件失败时任务判失败并列出未搬动的文件名, 失败不影响已完成的刮削结果。

三个目录 (输入 / 成功 / 失败) 都可选, 只要填了至少一个就成立. `MediaFile.path` 因此可以落在
库根之外, 判断一条记录是否还属于这个库要看 `library/rules.py::scope_roots` 给的那组目录,
不能只比库根 —— 整理前的剪枝、刷新的「已消失」判定都按它来; 洗版只认 `publish_roots`
(库根与成功目录), 输入目录里是待整理、失败目录里是待复制, 都不参与「留最优」.

落点就是库根 (填了输入目录、成功目录留空) 且库开了 `auto_organize` 时, 转移任务自己的后继里再排
一次该文件的 `ORGANIZE`: 开启转移后刮削链不再排整理, 少了这一步文件会以原名平铺在库根。整理排在
转移之后, 两者顺序执行, 不会争同一把库锁。落点是单独的成品目录时不整理 —— 那是使用者排好的树。

搬完之后还会: 按新目录重算字幕角标、丢弃该库的清理清单 (其中的旧路径已失效)、排一次
`MEDIA_REFRESH` (开关同 `media_server.auto_refresh`)。



- 不新增鉴权豁免。五个路由都走全局 token 中间件。
- 不在 `api/routes/` 里跑文件遍历或网络请求。
- 不写第二个状态源 (旧面板的 JSON / 内存字典) 与数据库并存。
- 不用 `hasattr` / `getattr` 探测可选依赖, 缺失就走 typed 分支。
